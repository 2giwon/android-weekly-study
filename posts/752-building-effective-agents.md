## 한 줄 요약

Anthropic이 수십 개 팀과 LLM 에이전트를 만들며 배운 것은, **가장 잘된 팀들은 복잡한 프레임워크가 아니라 단순하고 조합하기 쉬운 패턴으로 만들었다**는 것이다. 이 글은 "에이전트"를 미리 정한 길로 도는 **워크플로**와 LLM이 스스로 길을 정하는 **에이전트**로 나누고, 도구와 검색과 기억을 붙인 LLM 하나에서 시작해 프롬프트 사슬, 분기, 병렬, 지휘자와 일꾼, 평가자와 개선자, 자율 에이전트까지 복잡도를 한 단계씩 올려 가며 언제 무엇을 쓰는지 정리한다. 결론은 **가장 단순한 해법을 찾고, 결과가 눈에 띄게 좋아질 때만 복잡도를 더하라**는 것이다.

## 먼저 알아 둘 말

- **LLM(Large Language Model)**
  - 글을 읽고 글을 써 내는 큰 AI 모델이다. Claude, GPT, Gemini가 여기에 든다. 앱이 LLM을 "부른다"는 것은 글(프롬프트)을 API로 보내고 답을 받는다는 뜻이다.
- **에이전트 시스템(agentic system), 워크플로(workflow), 에이전트(agent)**
  - 원문은 LLM과 도구를 엮은 것을 모두 **에이전트 시스템**이라고 부르고, 그 안을 둘로 나눈다.
  - **워크플로**: LLM과 도구가 **개발자가 코드로 미리 정한 길**을 따라 돈다. Android로 치면 순서가 정해진 함수 호출 사슬이다.
  - **에이전트**: LLM이 **스스로** 다음에 무엇을 할지, 어떤 도구를 쓸지 정한다. 길이 실행 중에 정해진다.
- **도구(tool), 도구 사용(tool use), function calling**
  - LLM이 답 대신 "이 함수를 이 인자로 불러 달라"는 요청을 내는 기능이다. 앱이 그 함수를 실제로 실행하고 결과를 다시 LLM에 넘긴다. Aide 결정 기록의 `create_event`, `propose_task` 같은 AI 함수가 도구다.
- **검색 증강(retrieval)**
  - LLM이 답하기 전에 필요한 자료를 찾아 프롬프트에 넣는 것이다. 예를 들면 오늘 일정 목록을 찾아서 같이 보내는 것이다.
- **컨텍스트 안 예시(in-context examples)**
  - 프롬프트 안에 "이런 입력에는 이렇게 답한다"는 예를 몇 개 넣어 주는 것이다. 모델을 다시 학습시키지 않고 답의 모양을 맞추는 방법이다.
- **MCP(Model Context Protocol)**
  - Anthropic이 공개한 규약으로, LLM 앱이 바깥 도구와 자료에 붙는 방식을 하나로 맞춘다. 규약을 따르는 도구 서버라면 어느 LLM 앱에든 꽂아 쓸 수 있다.
- **게이트(gate)**
  - 단계 사이에 두는 **코드로 된 검사**다. 앞 단계의 결과가 조건을 채우지 못하면 다음 단계로 가지 않고 멈춘다.
- **가드레일(guardrail)**
  - LLM이 하면 안 되는 일이나 내면 안 되는 답을 막는 장치다.
- **평가(eval)**
  - LLM의 답이 얼마나 좋은지 여러 입력으로 재 보는 시험이다. 앱의 단위 시험처럼, 프롬프트를 바꿀 때마다 돌려 나빠지지 않았는지 본다.
- **지연(latency)**
  - 요청을 보내고 답이 오기까지 걸리는 시간이다. LLM을 여러 번 부르면 지연과 비용이 함께 는다.
- **SWE-bench**
  - 실제 GitHub 이슈를 주고 코드를 고쳐 시험을 통과하는지 보는 코딩 에이전트 평가 묶음이다. Verified는 사람이 검증한 문제만 모은 판이다.
- **ACI(agent-computer interface)**
  - 원문이 만든 말이다. 사람이 쓰는 화면을 HCI(human-computer interface)라고 하듯, **에이전트가 쓰는 도구의 이름, 설명, 인자 모양**을 ACI라고 부른다.
- **포카요케(poka-yoke)**
  - 일본 제조업에서 온 말로 "실수를 막는 장치"다. 애초에 틀리게 끼울 수 없는 플러그 모양처럼, 실수할 여지 자체를 없애는 설계를 말한다.

## 에이전트란 무엇인가

- **"에이전트"라는 말은 여러 뜻으로 쓰인다**
  - 어떤 고객은 오랫동안 혼자 돌며 여러 도구로 복잡한 일을 끝내는 완전 자율 시스템을 에이전트라고 부른다.
  - 다른 고객은 미리 정한 워크플로를 따르는, 훨씬 정해진 구현을 에이전트라고 부른다.
- **Anthropic은 이 모두를 "에이전트 시스템"으로 묶고, 구조에서 중요한 선을 하나 긋는다**
  - **워크플로**는 LLM과 도구를 **미리 정한 코드 경로**로 엮은 시스템이다.
  - **에이전트**는 LLM이 **자기 과정과 도구 사용을 스스로 이끌고**, 일을 어떻게 끝낼지에 대한 통제권을 쥔 시스템이다.
- 원문은 아래에서 두 종류를 자세히 보고, 부록 1에서 고객들이 특히 가치를 본 두 분야를 소개한다.

## 언제 에이전트를 쓰고, 언제 쓰지 말까

- **가장 단순한 해법을 먼저 찾고, 필요할 때만 복잡도를 올린다**
  - 이것은 **에이전트 시스템을 아예 만들지 않는 것**일 수도 있다.
  - 왜: 에이전트 시스템은 대개 지연과 비용을 내주고 더 나은 성능을 얻는다. 그 맞바꿈이 맞는지 따져 봐야 한다.
- **복잡도가 정말 필요할 때**
  - 잘 정의된 일에는 워크플로가 예측 가능하고 일관된 결과를 준다.
  - 유연함과 모델이 내리는 판단이 큰 규모로 필요할 때는 에이전트가 낫다.
- **그러나 많은 앱에서는** 검색 증강과 컨텍스트 안 예시로 **LLM 호출 한 번을 잘 다듬는 것으로 대개 충분하다.**

## 프레임워크는 언제, 어떻게 쓸까

- **에이전트 시스템을 쉽게 만들어 주는 프레임워크가 많다**
  - Claude Agent SDK
  - AWS의 Strands Agents SDK
  - Rivet: 끌어다 놓는 화면으로 LLM 워크플로를 만드는 도구
  - Vellum: 복잡한 워크플로를 만들고 시험하는 또 하나의 화면 도구
- **장점**: LLM 부르기, 도구 정의와 해석, 호출 잇기 같은 기본적인 저수준 일을 쉽게 해 줘서 시작이 빠르다.
- **단점**
  - 추상화 계층이 하나 더 생겨, 그 아래에서 실제로 오가는 프롬프트와 응답을 가린다. 그래서 고장을 찾기 어려워진다.
  - 더 단순한 구성으로 충분한데도 복잡도를 더하고 싶은 유혹이 생긴다.
- **원문의 권고**
  - 먼저 **LLM API를 직접** 써서 시작하라. 많은 패턴은 코드 몇 줄이면 된다.
  - 프레임워크를 쓴다면 **그 아래 코드를 이해하라.** "안에서 이렇게 돌겠지" 하는 잘못된 짐작이 고객 실수의 흔한 원인이다.
  - 예시 구현은 Anthropic의 cookbook(예제 모음)에 있다.

## 구성 요소, 워크플로, 에이전트

원문은 실제 서비스에서 본 흔한 패턴을, 기본 구성 요소인 **증강된 LLM**에서 시작해 단순한 조합 워크플로를 지나 자율 에이전트까지 복잡도를 차례로 올려 가며 설명한다.

### 기본 구성 요소: 증강된 LLM

- **에이전트 시스템의 기본 단위는 검색, 도구, 기억 같은 능력을 붙인 LLM이다**
  - 지금 모델은 이 능력을 스스로 쓴다. 검색어를 직접 만들고, 알맞은 도구를 고르고, 무엇을 기억해 둘지 정한다.

<figure class="media"><img src="https://assets.claude.com/bba3d0e7336751fea8440726d52709047334962d.png" alt="입력이 LLM을 지나 출력으로 가고, LLM이 검색, 도구, 기억과 점선으로 주고받는 그림" loading="lazy"><figcaption>원문 그림 "증강된 LLM". 왼쪽 In(입력)에서 가운데 LLM을 지나 오른쪽 Out(출력)으로 간다. Retrieval(검색)과는 질의와 결과를, Tools(도구)와는 호출과 응답을, Memory(기억)와는 읽기와 쓰기를 주고받는다. 원문 서버에서 불러옴 (<a href="https://www.anthropic.com/research/building-effective-agents">원문</a>)</figcaption></figure>

- **구현에서 집중할 두 가지**
  - 이 능력들을 **내 쓰임새에 맞게** 다듬는다.
  - LLM이 쓰기 쉽고 설명이 잘된 창구를 준다.
- 구현 방법은 여러 가지이고, 그중 하나가 MCP다. 단순한 클라이언트 하나만 만들면 늘어나는 바깥 도구 생태계에 붙을 수 있다.
- 원문은 이 뒤로 **모든 LLM 호출이 이 능력들을 쓸 수 있다고 가정한다.**

### 워크플로: 프롬프트 사슬(prompt chaining)

- **무엇을**: 일을 여러 단계로 쪼개고, 각 LLM 호출이 앞 호출의 결과를 받아 처리한다. 중간 단계 어디에든 코드로 된 검사(게이트)를 넣어 흐름이 제대로 가고 있는지 확인할 수 있다.

<figure class="media"><img src="https://assets.claude.com/430f593e41769039c477d3e4d6222dc9ad304816.png" alt="입력, LLM 호출 1, 게이트, 통과하면 LLM 호출 2와 3을 지나 출력, 실패하면 종료로 가는 그림" loading="lazy"><figcaption>원문 그림 "프롬프트 사슬 워크플로". In에서 LLM Call 1로 가고, 그 결과(Output 1)가 Gate(게이트)로 간다. 게이트를 통과(Pass)하면 LLM Call 2, 그 결과(Output 2)가 LLM Call 3을 지나 Out으로 간다. 게이트에서 실패(Fail)하면 점선을 따라 Exit(종료)로 빠진다. 원문 서버에서 불러옴 (<a href="https://www.anthropic.com/research/building-effective-agents">원문</a>)</figcaption></figure>

- **언제 쓰나**: 일을 고정된 하위 작업으로 쉽고 깔끔하게 나눌 수 있을 때다. 각 호출을 더 쉬운 일로 만드는 대신 지연을 내주고 정확도를 얻는 것이 목적이다.
- **쓸모 있는 예**
  - 광고 문구를 만든 다음 다른 언어로 옮기기
  - 문서의 개요를 쓰고, 개요가 조건을 채우는지 확인한 다음, 개요대로 문서 쓰기

### 워크플로: 분기(routing)

- **무엇을**: 입력을 분류해서 그 종류에 맞는 전문 후속 작업으로 보낸다.
- **왜**: 관심사를 나누고 더 전문적인 프롬프트를 만들 수 있다. 이 워크플로가 없으면 한 종류의 입력에 맞춰 다듬은 것이 다른 입력의 성능을 떨어뜨릴 수 있다.

<figure class="media"><img src="https://assets.claude.com/65050af354d6cb7a930735dc3c6f6e693b9385a4.png" alt="입력이 분기 LLM 호출로 가고, 세 LLM 호출 중 하나로 보내진 뒤 출력으로 가는 그림" loading="lazy"><figcaption>원문 그림 "분기 워크플로". In에서 LLM Call Router(분기를 정하는 호출)로 간다. 분기 호출에서 LLM Call 1, 2, 3으로 화살표가 나가는데, 1번으로 가는 화살표만 실선이고 2번과 3번은 점선이다. 셋 중 하나만 골라 간다는 뜻이다. 세 호출 모두 Out으로 이어진다. 원문 서버에서 불러옴 (<a href="https://www.anthropic.com/research/building-effective-agents">원문</a>)</figcaption></figure>

- **언제 쓰나**: 따로 다루는 편이 나은 뚜렷한 종류가 있고, 그 분류를 LLM이나 전통적인 분류 모델 또는 알고리즘으로 정확하게 할 수 있는 복잡한 일에 맞다.
- **쓸모 있는 예**
  - 고객 상담 질문을 일반 질문, 환불 요청, 기술 지원으로 나눠 서로 다른 후속 과정, 프롬프트, 도구로 보내기
  - 쉽고 흔한 질문은 Claude Haiku 4.5 같은 작고 싼 모델로, 어렵고 드문 질문은 Claude Sonnet 4.5 같은 더 강한 모델로 보내 성능과 비용을 함께 맞추기

### 워크플로: 병렬(parallelization)

- **무엇을**: LLM 여러 개가 한 일을 동시에 하고, 그 결과를 코드로 모은다. 두 가지 갈래가 있다.
  - **나누기(sectioning)**: 일을 서로 무관한 하위 작업으로 쪼개 동시에 돌린다.
  - **투표(voting)**: 같은 일을 여러 번 돌려 다양한 결과를 얻는다.

<figure class="media"><img src="https://assets.claude.com/1ac29508ce49cac6f58ec37dd360982dd618cbaa.png" alt="입력이 세 LLM 호출로 동시에 갈라지고, 모으는 곳을 지나 출력으로 가는 그림" loading="lazy"><figcaption>원문 그림 "병렬 워크플로". In에서 LLM Call 1, 2, 3으로 실선 화살표 세 개가 동시에 나간다. 세 호출의 결과는 모두 Aggregator(모으는 곳)로 들어가고, 거기서 Out으로 간다. 분기 그림과 달리 세 화살표가 모두 실선이라 셋 다 돈다는 뜻이다. 원문 서버에서 불러옴 (<a href="https://www.anthropic.com/research/building-effective-agents">원문</a>)</figcaption></figure>

- **언제 쓰나**: 나눈 하위 작업을 동시에 돌려 빨라질 수 있을 때, 또는 더 믿을 만한 결과를 위해 여러 관점이나 여러 번의 시도가 필요할 때다. 고려할 것이 여러 가지인 복잡한 일에서는, 고려 사항마다 따로 LLM을 부르는 편이 각 측면에 집중할 수 있어 대개 더 잘한다.
- **쓸모 있는 예**
  - 나누기
    - 가드레일: 한 모델이 사용자 질문을 처리하는 동안 다른 모델이 부적절한 내용이나 요청을 걸러 낸다. 같은 호출이 가드레일과 본 답을 함께 맡는 것보다 대체로 잘된다.
    - 평가 자동화: LLM 호출마다 주어진 프롬프트에 대한 모델 성능의 서로 다른 측면을 평가한다.
  - 투표
    - 코드 취약점 검토: 서로 다른 프롬프트 여러 개가 코드를 검토하고, 문제를 찾으면 표시한다.
    - 내용이 부적절한지 판단: 여러 프롬프트가 서로 다른 측면을 보거나, 서로 다른 투표 기준을 둬서 잘못 잡는 것과 놓치는 것 사이 균형을 맞춘다.

### 워크플로: 지휘자와 일꾼(orchestrator-workers)

- **무엇을**: 가운데 LLM(지휘자)이 일을 그때그때 쪼개 일꾼 LLM들에게 맡기고, 결과를 합친다.

<figure class="media"><img src="https://assets.claude.com/c8fc5373e187c2e37ab755fac1cf82b3bf366718.png" alt="입력이 지휘자로 가고, 지휘자가 점선으로 세 LLM 호출에 일을 맡긴 뒤 합치는 곳을 지나 출력으로 가는 그림" loading="lazy"><figcaption>원문 그림 "지휘자와 일꾼 워크플로". In에서 Orchestrator(지휘자)로 간다. 지휘자에서 LLM Call 1, 2, 3으로 점선 화살표가 나가고, 세 호출의 결과가 점선으로 Synthesizer(합치는 곳)에 들어간 뒤 Out으로 간다. 병렬 그림과 모양은 비슷하지만 화살표가 점선이라, 몇 개를 어떻게 맡길지 지휘자가 그때 정한다는 뜻이다. 원문 서버에서 불러옴 (<a href="https://www.anthropic.com/research/building-effective-agents">원문</a>)</figcaption></figure>

- **언제 쓰나**: 필요한 하위 작업을 미리 알 수 없는 복잡한 일에 잘 맞는다. 코딩이 그렇다. 몇 개 파일을 고쳐야 하는지, 각 파일을 어떻게 고쳐야 하는지가 일에 따라 다르다.
- **병렬과 다른 점**: 그림 모양은 비슷하지만 핵심 차이는 **유연함**이다. 하위 작업이 미리 정해져 있지 않고, 입력을 본 지휘자가 정한다.
- **쓸모 있는 예**
  - 매번 여러 파일을 복잡하게 고치는 코딩 제품
  - 여러 출처에서 관련 있을 만한 정보를 모으고 분석하는 검색 작업

### 워크플로: 평가자와 개선자(evaluator-optimizer)

- **무엇을**: 한 LLM 호출이 답을 만들고, 다른 호출이 평가와 피드백을 주는 것을 고리로 반복한다.

<figure class="media"><img src="https://assets.claude.com/4b2dd710371f70a2380356de4ee3ebbf902f319c.png" alt="입력이 생성 LLM 호출로 가고, 생성한 답을 평가 LLM 호출이 받아 통과하면 출력, 거절하면 피드백과 함께 되돌려 보내는 고리 그림" loading="lazy"><figcaption>원문 그림 "평가자와 개선자 워크플로". In에서 LLM Call Generator(만드는 호출)로 간다. 만든 답(Solution)이 위쪽 화살표로 LLM Call Evaluator(평가하는 호출)에 가고, 평가가 받아들이면(Accepted) Out으로 간다. 받아들이지 않으면 아래쪽 화살표로 거절과 피드백(Rejected + Feedback)을 만드는 호출에 되돌려 보낸다. 원문 서버에서 불러옴 (<a href="https://www.anthropic.com/research/building-effective-agents">원문</a>)</figcaption></figure>

- **언제 쓰나**: 평가 기준이 분명하고, 거듭 다듬는 것이 눈에 보이는 가치를 줄 때 특히 잘 맞는다. 잘 맞는다는 신호는 둘이다.
  - 사람이 피드백을 말로 해 주면 LLM의 답이 눈에 띄게 좋아진다.
  - LLM도 그런 피드백을 줄 수 있다.
  - 사람 작가가 다듬어진 글을 내기까지 고쳐 쓰는 과정과 비슷하다.
- **쓸모 있는 예**
  - 문학 번역: 번역하는 LLM이 처음엔 놓친 미묘한 뜻을, 평가하는 LLM이 쓸모 있는 비평으로 짚어 줄 수 있다.
  - 여러 번 검색하고 분석해야 충분한 정보를 모을 수 있는 복잡한 검색: 평가자가 검색을 더 해야 할지 정한다.

### 에이전트

- **LLM이 핵심 능력에서 성숙해지면서 실제 서비스에 에이전트가 나타나고 있다**
  - 복잡한 입력을 이해하기, 추론하고 계획하기, 도구를 믿을 만하게 쓰기, 오류에서 회복하기다.
- **에이전트가 일하는 순서**
  - 사람의 명령이나 대화로 일을 시작한다.
  - 일이 분명해지면 스스로 계획하고 움직인다. 정보나 판단이 더 필요하면 사람에게 돌아올 수 있다.
  - 실행하는 동안 **단계마다 환경에서 "실제 결과(ground truth)"를 얻는 것**이 아주 중요하다. 도구 호출 결과나 코드 실행 결과로 진행 상황을 판단한다.
  - 확인 지점이나 막혔을 때 멈추고 사람의 피드백을 받을 수 있다.
  - 일은 대개 끝나면 멈추지만, 통제를 위해 **멈춤 조건**(예: 최대 반복 횟수)을 두는 것도 흔하다.
- **에이전트는 어려운 일을 하지만, 구현은 대개 단순하다**
  - 보통은 **환경의 피드백을 보며 도구를 쓰는 LLM을 고리로 돌리는 것**이 전부다.
  - 그래서 도구 묶음과 그 설명을 분명하고 세심하게 설계하는 것이 아주 중요하다. 원문은 부록 2에서 도구 개발 모범 사례를 다룬다.

<figure class="media"><img src="https://assets.claude.com/ecba32d35b19d94e892c3c89c3bf59b130e25eb0.png" alt="사람과 LLM 호출이 점선으로 주고받고, LLM 호출이 환경에 행동을 보내고 피드백을 받는 고리, 그리고 멈춤으로 가는 점선이 있는 그림" loading="lazy"><figcaption>원문 그림 "자율 에이전트". 왼쪽 Human(사람)과 가운데 LLM Call이 점선 양방향 화살표로 이어져 있다. LLM Call은 오른쪽 Environment(환경)에 Action(행동)을 보내고 Feedback(피드백)을 받는 고리를 돈다. LLM Call 아래로 점선이 Stop(멈춤)으로 내려간다. 원문 서버에서 불러옴 (<a href="https://www.anthropic.com/research/building-effective-agents">원문</a>)</figcaption></figure>

- **언제 쓰나**: 필요한 단계 수를 예측하기 어렵거나 불가능하고, 길을 코드로 고정할 수 없는 열린 문제에 쓴다. LLM이 여러 차례 돌 수 있으므로, 그 판단을 어느 정도 믿을 수 있어야 한다. 자율성 덕분에 **믿을 수 있는 환경에서** 일을 크게 늘려 돌리기에 좋다.
- **대가**: 자율적이라 비용이 크고, 오류가 쌓여 커질 위험이 있다. 원문은 격리된 환경(sandbox)에서 많이 시험하고 알맞은 가드레일을 두라고 권한다.
- **쓸모 있는 예** (Anthropic이 직접 만든 것)
  - 작업 설명을 보고 여러 파일을 고쳐 SWE-bench 문제를 푸는 코딩 에이전트
  - Claude가 컴퓨터를 써서 일을 끝내는 "computer use" 참고 구현

## 패턴을 섞고 고쳐 쓰기

- 위 구성 요소들은 **정해진 처방이 아니다.** 개발자가 쓰임새에 맞게 모양을 바꾸고 섞어 쓰는 흔한 패턴이다.
- 성공의 열쇠는 다른 LLM 기능과 같다. **성능을 재고, 구현을 거듭 고친다.**
- 원문은 한 번 더 강조한다. **복잡도는 결과를 눈에 띄게 좋게 만들 때만 더하라.**

## 정리

- **LLM 분야의 성공은 가장 정교한 시스템을 만드는 것이 아니라, 내 필요에 맞는 시스템을 만드는 것이다.**
  - 단순한 프롬프트로 시작하고, 넓은 평가로 다듬고, 더 단순한 해법이 모자랄 때만 여러 단계의 에이전트 시스템을 더한다.
- **에이전트를 만들 때 Anthropic이 지키려는 세 원칙**
  1. 에이전트 설계를 **단순하게** 둔다.
  2. 에이전트의 계획 단계를 분명히 보여 줘서 **투명함**을 우선한다.
  3. 도구 설명과 시험을 꼼꼼히 해서 **ACI를 공들여 만든다.**
- 프레임워크는 빨리 시작하게 도와주지만, 실제 서비스로 갈 때는 추상화 계층을 줄이고 기본 부품으로 만드는 것을 망설이지 말라고 한다. 그래야 강력할 뿐 아니라 믿을 만하고, 관리하기 쉽고, 사용자가 믿는 에이전트가 된다.

## 부록 1: 실제로 쓰이는 에이전트

고객과 일하며 특히 유망하다고 본 두 분야다. 둘 다 에이전트가 가장 가치를 내는 일의 조건을 보여 준다. **대화와 행동이 함께 필요하고, 성공 기준이 분명하고, 피드백 고리를 돌 수 있고, 사람이 의미 있게 지켜볼 수 있는 일**이다.

### 가. 고객 상담

- 익숙한 챗봇 화면에 도구 연동으로 능력을 더한다. 더 열린 에이전트에 잘 맞는 이유는 넷이다.
  - 상담은 자연스럽게 대화 흐름을 따르면서도 바깥 정보와 행동이 필요하다.
  - 고객 정보, 주문 기록, 도움말 문서를 가져오는 도구를 붙일 수 있다.
  - 환불이나 상담 기록 갱신 같은 행동을 코드로 처리할 수 있다.
  - 사용자가 정한 해결 여부로 성공을 분명히 잴 수 있다.
- 여러 회사가 **해결한 건에만 돈을 받는 요금제**로 이 방식이 통한다는 것을 보여 줬다. 자기 에이전트가 잘한다는 자신감의 표시다.

### 나. 코딩 에이전트

- 소프트웨어 개발은 LLM 기능의 가능성이 크게 드러난 분야다. 코드 자동 완성에서 스스로 문제를 푸는 데까지 능력이 자랐다. 에이전트가 특히 잘 맞는 이유는 넷이다.
  - 코드 해법은 자동 시험으로 검증할 수 있다.
  - 에이전트가 시험 결과를 피드백 삼아 해법을 거듭 고칠 수 있다.
  - 문제 공간이 잘 정의돼 있고 구조가 있다.
  - 결과물의 품질을 객관적으로 잴 수 있다.
- Anthropic의 구현은 이제 SWE-bench Verified의 실제 GitHub 이슈를 PR 설명만 보고 풀 수 있다. 그래도 자동 시험은 기능이 도는지만 확인해 줄 뿐이라, **해법이 시스템 전체의 요구와 맞는지는 여전히 사람의 검토가 중요하다.**

## 부록 2: 도구도 프롬프트처럼 공들이기

- **어떤 에이전트 시스템을 만들든 도구는 중요한 부분이 된다**
  - 도구는 API에 정확한 구조와 정의를 적어 Claude가 바깥 서비스와 API를 다룰 수 있게 한다. Claude가 도구를 쓰려고 하면 API 응답에 도구 사용 블록이 들어 있다.
  - 도구 정의와 명세에도 전체 프롬프트만큼의 공을 들여야 한다.
- **같은 행동을 적는 방법은 여러 가지다**
  - 파일 수정을 diff(바뀐 줄만 적은 형식)로 쓸 수도, 파일 전체를 다시 쓸 수도 있다. 구조화된 출력을 markdown 안 코드로도, JSON 안 코드로도 돌려줄 수 있다.
  - 소프트웨어 공학에서는 이런 차이가 겉모양일 뿐이고 서로 손실 없이 바꿀 수 있다. 하지만 **LLM에게는 어떤 형식은 훨씬 쓰기 어렵다.**
  - diff를 쓰려면 새 코드를 쓰기 전에 덩어리 머리말에 바뀌는 줄 수를 먼저 알아야 한다. JSON 안에 코드를 쓰면 markdown과 달리 줄바꿈과 따옴표를 모두 이스케이프(특수 문자 앞에 표시를 붙이는 것)해야 한다.
- **도구 형식을 정할 때의 제안**
  - 모델이 스스로 궁지에 몰리기 전에 "생각할" 토큰을 충분히 준다.
  - 인터넷 글에서 모델이 자연스럽게 본 형식에 가깝게 둔다.
  - 형식 때문에 생기는 부담을 없앤다. 수천 줄을 정확히 세게 하거나, 쓰는 코드를 모두 이스케이프하게 하지 않는다.
- **사람용 화면(HCI)에 들이는 만큼 ACI에도 공을 들인다**
  - **모델 입장에서 생각한다.** 설명과 인자만 보고 이 도구를 어떻게 쓸지 바로 알 수 있는가, 아니면 곰곰이 생각해야 하는가? 생각해야 한다면 모델도 그렇다. 좋은 도구 정의에는 사용 예, 경계 사례, 입력 형식 요구, 다른 도구와의 분명한 경계가 들어 있다.
  - **인자 이름과 설명을 바꿔 더 분명하게 만들 수 있는가?** 팀의 신입 개발자에게 줄 좋은 설명 주석을 쓴다고 생각한다. 비슷한 도구가 많을 때 특히 중요하다.
  - **모델이 도구를 어떻게 쓰는지 시험한다.** 콘솔(workbench)에서 예시 입력을 많이 돌려 어떤 실수를 하는지 보고 고친다.
  - **도구에 포카요케를 건다.** 인자를 바꿔 실수하기 어렵게 만든다.
- **실제 사례**
  - SWE-bench 에이전트를 만들 때 Anthropic은 전체 프롬프트보다 **도구를 다듬는 데 시간을 더 썼다.**
  - 에이전트가 루트 폴더 밖으로 옮겨 간 뒤에 상대 경로를 쓰는 도구에서 모델이 실수했다. 도구가 **언제나 절대 경로를 요구하도록** 바꿨더니 모델이 그 방식을 흠 없이 썼다.

## 코드로 보기 — Aide 구조로 옮긴 스케치

원문에는 코드가 없다. 아래는 모두 **직접 쓴 스케치**이고, Aide 결정 기록의 AI 함수 이름(`create_event`, `propose_event`, `propose_task`, `ask_completion`)과 1-b 기능을 따랐다. 1-b는 아직 시작 전이라 모듈과 클래스 이름은 가정이고, 빌드해 보지 않았다.

**1. 기능마다 가장 단순한 패턴 고르기**

```kotlin
// 1-b 설계 메모 — 직접 쓴 스케치
enum class AiPattern { NO_LLM, SINGLE_CALL, CHAIN, TOOL_LOOP }

val aideFeatures = mapOf(
    "완료 확인 질문" to AiPattern.NO_LLM,
    "아침 브리핑" to AiPattern.CHAIN,
    "말로 일정이나 할 일 만들기" to AiPattern.SINGLE_CALL,
    "여러 날에 걸친 계획 세우기" to AiPattern.TOOL_LOOP,
)
```

- `NO_LLM`
  - 완료 확인 질문("캘린더 작업이 완료되었나요?")은 마감이 오늘인 할 일을 고르는 **규칙**이라 LLM이 필요 없다. 2026-10-08 결정도 "기술적으로는 규칙"이라고 적었다. 원문의 "에이전트 시스템을 아예 만들지 않는 것"이 여기다.
- `CHAIN`
  - 아침 브리핑은 원문의 프롬프트 사슬이다. 1단계 "오늘 일정 3, 마감 할 일 2"를 **코드로** 센다(08:30 숫자 알림이 이미 이 일을 한다). 2단계 그 숫자와 목록을 넣어 LLM을 한 번 불러 문장을 만든다. 1단계와 2단계 사이에 "숫자가 0이면 LLM을 부르지 않는다" 같은 게이트를 둘 수 있다.
- `SINGLE_CALL`
  - "내일 3시 디자인 회의 잡아줘"는 도구 하나(`create_event`)를 고르는 LLM 호출 한 번이면 된다. 원문의 "증강된 LLM" 한 번이다.
- `TOOL_LOOP`
  - LLM이 도구를 여러 번 부르며 스스로 길을 정하는 진짜 에이전트다. 1-b 범위에는 없고, 예시로만 남겼다.

**2. 도구 정의에 포카요케 걸기**

```kotlin
// core:ai (1-b, 가정한 모듈) — 직접 쓴 스케치
val createEventTool = ToolSpec(
    name = "create_event",
    description = """
        사용자가 직접 시킨 일정을 기본 캘린더에 바로 넣는다.
        사용자가 시키지 않았는데 AI가 떠올린 일정에는 쓰지 말고 propose_event를 쓴다.
        예: "내일 3시 디자인 회의" -> {"title":"디자인 회의","start":"2026-11-14T15:00","durationMinutes":60}
    """.trimIndent(),
    inputSchema = buildJsonObject {
        put("type", "object")
        putJsonObject("properties") {
            putJsonObject("title") { put("type", "string") }
            putJsonObject("start") {
                put("type", "string")
                put("description", "기기 시간대 기준 절대 날짜와 시각. yyyy-MM-ddTHH:mm. '내일', '다음 주' 같은 말은 쓰지 않는다")
            }
            putJsonObject("durationMinutes") { put("type", "integer"); put("minimum", 5) }
        }
        putJsonArray("required") { add("title"); add("start"); add("durationMinutes") }
    },
)

fun systemPrompt(now: ZonedDateTime) = """
    지금은 ${now.toLocalDateTime().truncatedTo(ChronoUnit.MINUTES)} (${now.zone}) 이다.
    날짜는 언제나 이 시각을 기준으로 계산해 절대 날짜로 적는다.
""".trimIndent()
```

- `description` 의 두 번째 줄
  - 원문이 말한 "다른 도구와의 분명한 경계"다. `create_event` 와 `propose_event` 는 이름이 비슷해 헷갈리기 쉽다. 「시킨 일은 바로 하고, 시키지 않은 일은 묻는다」(2026-10-08)를 도구 설명에 그대로 적어 둔다.
- `description` 의 예시 한 줄
  - 원문이 말한 "사용 예"다.
- `start` 를 절대 날짜로만 받기
  - 원문의 "상대 경로 대신 절대 경로" 사례를 Aide 일정으로 옮긴 것이다. LLM이 "내일"을 그대로 넘기면 앱이 해석하다 틀릴 수 있고, 자정 무렵이나 시간대가 바뀐 출장지에서 특히 어긋난다(계획 Review Focus 2번의 시간대 문제). 지금 시각과 시간대를 시스템 프롬프트에 넣어 주고, 도구는 절대 값만 받는다.
- 캘린더 id 인자가 **없다**
  - 어느 캘린더에 넣을지는 결정 기록대로 앱이 기본 캘린더로 정한다. LLM이 고를 여지를 아예 주지 않는 것도 포카요케다.

**3. 도구를 실행한 뒤 실제 결과를 다시 읽기**

```kotlin
// core:ai (1-b, 가정한 모듈) — 직접 쓴 스케치
suspend fun runCreateEvent(input: CreateEventInput): ToolResult {
    val start = runCatching { LocalDateTime.parse(input.start) }.getOrNull()
        ?: return ToolResult.error("start는 yyyy-MM-ddTHH:mm 형식이어야 한다: ${input.start}")
    val calendarId = settings.defaultCalendarId()
        ?: return ToolResult.error("기본 캘린더가 정해져 있지 않다")

    val eventId = eventRepository.insertEvent(input.toDraft(start, calendarId))
    val saved = eventRepository.findEvent(eventId)
        ?: return ToolResult.error("일정을 넣었지만 캘린더에서 다시 찾지 못했다")

    activityLog.recordUndoable(AiAction.CreatedEvent(eventId))
    return ToolResult.ok("${saved.calendarName}에 ${saved.start} ${saved.title} 넣음")
}
```

- `LocalDateTime.parse` 실패를 오류 글로 돌려주기
  - 모양이 틀린 입력은 캘린더에 닿기 전에 막고, **무엇이 틀렸는지 글로** LLM에 돌려준다. LLM은 이 글을 보고 다시 시도할 수 있다.
- `findEvent(eventId)` 로 다시 읽기
  - 원문의 "단계마다 환경에서 실제 결과를 얻는다"다. 결과 카드가 "구글 캘린더(…)에 넣었어요"라고 말하기 전에, 정말로 폰 캘린더 저장소에 들어갔는지 확인한다.
- `activityLog.recordUndoable`
  - 결정 기록의 "바로 실행한 것은 활동 기록에 남기고 되돌릴 수 있어야 한다"를 지키는 자리다. 같은 이슈의 [Managed Agents 글](752-anthropic-managed-agents.html) 스케치에서 이 기록을 더 자세히 다룬다.

## 배운 점

- **"에이전트를 쓸까"보다 먼저 "LLM이 꼭 필요한가"를 묻는다.** 원문이 맨 먼저 권한 것이 "에이전트 시스템을 아예 만들지 않는 것"일 수도 있다는 말이었다.
- **워크플로와 에이전트를 가르는 기준은 "길을 누가 정하나"다.** 코드가 정하면 워크플로, LLM이 정하면 에이전트다. 이 기준 하나로 기능마다 어디에 둘지 정할 수 있다.
- **패턴은 다섯 개지만 뿌리는 하나다.** 도구, 검색, 기억을 붙인 LLM 한 번을 사슬로 잇거나, 갈라 보내거나, 동시에 돌리거나, 지휘자에게 맡기거나, 평가자와 고리로 돌린다.
- **에이전트의 구현은 생각보다 단순하고, 어려운 곳은 도구다.** "환경의 피드백을 보며 도구를 쓰는 LLM을 고리로 돌린다"가 전부라서, 결과의 질은 도구 이름과 설명과 인자 모양에서 갈린다.
- **도구의 실수는 프롬프트로 타이르지 말고 인자 모양으로 막는다.** 상대 경로에서 틀리던 모델이 절대 경로만 받게 바꾸자 흠 없이 썼다는 사례가 가장 기억에 남았다.
- **프레임워크는 아래를 이해할 때만 쓴다.** 추상화가 실제 프롬프트와 응답을 가리면 고장을 찾기 어려워진다.

## Aide에 적용하면

Aide 1-a(AI 없이 캘린더, 리마인더, 할 일, 대시보드)는 AI가 없으므로 이 글은 **1-b AI 설계**에 쓴다. 1-b는 아직 spec이 없고, 지금 정해진 것은 결정 기록뿐이다. 「LLM은 사용자가 고른 제공자를 사용자 키로 앱에서 직접 부른다」(2026-10-08), 「시킨 일은 AI가 바로 하고 되돌릴 수 있게, 시키지 않은 일은 묻는다」(2026-10-08), 「아침 브리핑: 08:30 숫자 알림은 확실하게, AI 브리핑은 미리 만들어 보고 안 되면 열 때」(2026-10-08), 「키가 없으면 AI 기능은 꺼지고 아바타는 잠든다」(2026-10-08)와 맞춰 썼다.

1. **1-b 기능을 하나씩 "가장 단순한 패턴"으로 분류한다 — 가져온다. 시점은 1-b spec을 쓸 때다.**
   - 무엇을: 위 스케치 1처럼 기능마다 "LLM 없음, LLM 한 번, 사슬, 도구 고리" 중 하나를 고르고 spec에 적는다.
   - 지금 보이는 분류: 완료 확인 질문은 LLM이 없는 규칙이다. 아침 브리핑은 "코드로 숫자를 센다, 그 다음 LLM을 한 번 불러 문장을 만든다"는 사슬이다. 말로 일정이나 할 일 만들기는 도구를 쓰는 LLM 한 번이다. 1-b 범위 안에는 LLM이 스스로 여러 단계를 도는 진짜 에이전트가 없다.
   - 왜: 사용자 키로 사용자가 요금을 내므로(2026-10-08 결정) LLM 호출 수가 곧 사용자의 돈이다. 원문의 "지연과 비용을 내주고 성능을 얻는 맞바꿈"을 Aide는 더 엄격하게 따져야 한다.
2. **Koog를 쓸지 정할 때 "실제 프롬프트와 응답을 볼 수 있나"를 기준에 넣는다 — 바꿔서 가져온다. 결정 기록과 약간 긴장이 있다.**
   - 2026-10-08 결정은 여러 제공자를 같은 방식으로 부르려고 Koog를 "검토하되, 안 되면 제공자별 API를 직접 부른다"로 남겼다. 원문은 "먼저 API를 직접 쓰고, 프레임워크를 쓰면 아래를 이해하라"고 권한다.
   - 바꾸는 점: 결정을 뒤집지 않는다. Koog 착수 전 확인 항목에 "Android에서 도는가"에 더해 **"보낸 프롬프트와 받은 응답을 그대로 기록해 볼 수 있는가"** 를 더한다. 볼 수 없다면 제공자 1곳으로 시작하는 1-b(2026-10-12 보강 결정)에서는 API를 직접 부르는 편이 낫다. 어느 쪽으로 할지는 사용자가 정한다.
3. **AI 함수 4개를 도구 설명과 인자 모양까지 공들여 만든다 — 가져온다. 시점은 1-b다.**
   - 무엇을: 스케치 2처럼 `create_event` 와 `propose_event` 의 경계를 설명에 쓰고, 사용 예를 넣고, 날짜는 **절대 날짜와 시각으로만** 받고, 캘린더 id는 인자로 주지 않는다.
   - 왜: 원문의 "절대 경로" 사례와 같다. 상대 날짜("내일")를 그대로 받으면 시간대가 바뀐 출장지나 자정 무렵에 어긋날 수 있다. 계획 Review Focus 2번(시간대와 서머타임)에서 이미 걱정한 문제다.
   - 같이 할 것: 사용자가 고르는 제공자마다 도구 사용 습관이 다를 수 있다. 원문의 "모델이 도구를 어떻게 쓰는지 많이 돌려 보라"를 따라, 1-b에서 예시 문장 묶음(예: "내일 3시 회의", "금요일 오후 두 시", "다음 주 월요일 아침")을 정해 두고 제공자를 바꿀 때마다 돌려 본다.
4. **도구를 실행한 뒤 실제 결과를 다시 읽고 나서 결과 카드를 보여 준다 — 가져온다. 시점은 1-b다.**
   - 무엇을: 스케치 3처럼 일정을 넣은 뒤 폰 캘린더 저장소에서 다시 읽어 확인하고, 그 값으로 "구글 캘린더(…)에 내일 15:00 디자인 회의 넣었어요" 카드를 만든다.
   - 왜: 원문이 "단계마다 환경에서 실제 결과를 얻는 것이 아주 중요하다"고 했다. 결정 기록의 "삼성 계정 캘린더에 다른 앱이 쓸 수 있는지 미검증"처럼 쓰기가 조용히 실패할 수 있는 자리가 Aide에 이미 있다.
5. **계획을 보여 주는 투명함 — 가져온다. #749와 같은 결론이다.** 원문의 세 원칙 중 둘째(계획 단계를 분명히 보여 준다)는 #749 [AI 에이전트는 계획부터 보여줘야 한다](749-ai-plan-first.html) 적용안과 같다. Aide의 결과 카드와 [되돌리기] 버튼이 그 자리다. 바꿀 것은 없다.
6. **평가자와 개선자, 투표 같은 여러 번 부르는 패턴 — 지금은 안 한다.**
   - 이유: 사용자 키로 사용자가 요금을 내고, 1-b 기능은 짧은 문장 하나나 도구 하나를 고르는 일이라 여러 번 다듬을 만한 가치가 작다.
   - 다시 볼 때: 2차의 작업 기록 기반 브리핑처럼 긴 글을 요약해야 하는 기능이 생길 때다.
7. **도구 고리를 도는 진짜 에이전트 — 지금은 안 한다. 만들게 되면 멈춤 조건부터 둔다.**
   - 1-b 범위에는 없다. 나중에 여러 날의 계획을 세우는 기능처럼 고리를 도는 기능이 생기면, 원문이 말한 **최대 반복 횟수**를 처음부터 둔다. 사용자 키로 도는 고리가 멈추지 않으면 사용자에게 요금이 계속 나간다.
